# Sprint 06 — Documentation Reconciliation

**Order:** 06 of 07  
**Theme:** Honesty  
**Audit reference:** Divergence matrix row 20 (documentation accuracy), §5.2 (expected artifacts define truth), §5.3 (replay simulated)

---

## Why this sprint exists

The audit found that documentation overstates implemented capabilities in several specific, traceable ways:

- `docs/process/V3.1_REAL_CORPUS_MANUAL.md` claims *"Decision Replay: ✅ Semantically proven with hard enforcement"* — at the time of the audit, this was false (all decisions were jail; see Sprint 05 for the fix)
- The V3.1 manual claims "20 directories processed deterministically" — at the time of the audit, this meant 20 directories were jailed on phantom data, not meaningfully processed
- `tests/real_corpus/expected_state.json` contained fabricated `sample-release-*` IDs manually invented, not produced by any system run
- `README.md` describes primary workflows as if they are production-ready

Documentation that overstates system capability erodes the very trust the product is designed to build. A user who reads the manual and then runs `make corpus-decide` will encounter behavior that does not match what they were told. This is the exact failure mode Resonance is designed to prevent in music metadata — it must not exhibit it in its own documentation.

This sprint brings documentation into alignment with the system state proven by Sprints 01–05.

---

## Problem statement

After Sprints 01–05, the system works. The documentation does not yet reflect what the system now does (and no longer does). Specific discrepancies to fix:

1. V3.1 manual claims and checklists still reference pre-Sprint-04 behavior (phantom evidence, all-jail corpus)
2. README implies workflows are production-ready without noting constraints or prerequisites
3. `expected_state.json` may have been regenerated by Sprint 04, but the V3.1 manual's narrative still describes the old state
4. No "Known Limitations" section exists anywhere in user-facing documentation

---

## Implementation requirements

1. **Audit every ✅ claim in the V3.1 manual.** For each checklist item marked ✅:
   - If the Sprint 01–05 evidence proves it true, leave it and add a reference to the sprint that proved it
   - If it is not yet true or is partially true, change it to a ⚠️ or ❌ marker with an accurate description
   - Never leave a ✅ on a claim that cannot be demonstrated by running a command

2. **Update the "20 directories processed deterministically" narrative.** Replace with accurate language describing what actually happened: how many directories were resolved to real release IDs, how many were jailed with actual reasoning, and what the evidence quality was.

3. **Update "Decision Replay: ✅ Semantically proven" only if Sprint 05 is complete.** This claim may only carry ✅ if the Sprint 05 replay proof test is passing and the evidence exists. If Sprint 05 is complete, cite the test. If Sprint 05 is not complete, mark as ⚠️ In Progress.

4. **Add "Known Limitations" to README.md.** The section should cover:
   - Provider API keys required for online mode (ACOUSTID_API_KEY, DISCOGS_TOKEN, MUSICBRAINZ_USERAGENT)
   - `make corpus-decide` requires a real music library at a configured path; it does not work on empty files
   - CI tests run in offline/cache-backed mode; online mode requires manual setup
   - Fingerprinting requires the `fpcalc` binary (AcoustID); if absent, fingerprint-based matching is unavailable

5. **Describe artifact provenance.** In the V3.1 manual or a README in `tests/real_corpus/`, document clearly that `expected_state.json`, `expected_layout.json`, and `expected_tags.json` are generated by running the system, not manually authored. Explain how to regenerate them.

6. **Do not add aspirational content.** This sprint is a reconciliation, not a roadmap. Do not add "coming soon" or "planned for V4" sections — those belong in `docs/process/versions/`.
